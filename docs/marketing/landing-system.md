# Операционная система лендингов

## Источники истины и решения

- **Product Facts** — актуальные проверенные знания о продукте, его доступности, ограничениях и доказательствах.
- **Landing Brief / Delta Brief** — утверждённое маркетинговое намерение и точные границы работы.
- **Явные решения пользователя** — единственный источник утверждения позиционирования, claims, текста, дизайна и публикации.

Синхронизация Product Facts и product-change handoff обновляют только знания. Они никогда не создают задачу, не меняют лендинг и не запускают workflow автоматически.

Отделяйте: `Решения`, `Факты и доказательства`, `Гипотезы`, `Неизвестное`. Факт описывает подтверждённое состояние продукта; маркетинговый claim — выбранную формулировку для аудитории. Одно не заменяет другое.

## Роли

- **marketing coordinator** ведёт процесс, границы, approvals и handoff;
- **researcher** собирает датированные источники и разделяет факты, выводы и неизвестное;
- **landing strategist** предлагает позиционирование и структуру в рамках brief;
- **copywriter** готовит текст по утверждённым фактам, claims и scope;
- **landing developer** реализует утверждённые текст и visual spec;
- **independent reviewer** проверяет фиксированные base/head, brief, preview и риски без исправления собственной проверки;
- **пользователь** — финальный владелец всех маркетинговых решений.

## Обязательные gates

1. Цель и positioning brief.
2. Copy.
3. Design / visual specification.
4. Publication.

Каждый gate требует точного одобрения пользователя. Одно одобрение может покрыть несколько gates только если они перечислены поимённо и показаны в точной версии.

## Жизненный цикл

Новый лендинг: заполненный brief → проверка фактов → утверждение цели/позиционирования → стратегия и copy → утверждение copy → design/visual spec → утверждение дизайна → реализация → preview → независимая проверка → отдельное разрешение публикации → merge/deploy → post-check.

Правка: точный Delta Brief → approvals для затронутых gates → реализация только delta → preview → независимая проверка → отдельное разрешение публикации → merge/deploy → post-check.

Сейчас merge в `main` публикует сайт через GitHub Pages. Механизм нужно проверять перед каждой публикацией: ветка, путь и настройки могут измениться. Review acceptance не разрешает merge или публикацию.

## Claims и эксперименты

Roadmap, `PLANNED`, `DEMAND TEST` и `CONCEPT` можно использовать снаружи только в точном утверждённом эксперименте. Внутренний статус не обязан быть публичной меткой. Нельзя выдавать проверяемую гипотезу или план за доступную функцию.

## Останов и откат

Остановить работу при отсутствии/расхождении brief, доказательств или approval; расширении scope; неоднозначном владельце решения; неожиданном drift base; риске недоступной поставки; невозможности независимой проверки или post-check.

До публикации откат — не сливать ветку. Для опубликованного изменения заранее указать восстанавливаемый commit/артефакт и способ возврата; выполнить откат только с соответствующей authority. После публикации проверить доступность, ключевой CTA, соответствие утверждённой версии и отсутствие неожиданных изменений.
